# Brown Octopus 0.6 Development and Test Plan

## Product direction

Brown Octopus is becoming a capability-routing gateway: the layer that
discovers, indexes, selects, constrains, and delivers the tools an agent needs
for its current task. The long-term managed product can provide a marketplace
of capabilities, access control, audit, policy, usage, and routing. Version
0.6 must first make the self-hosted routing core measurable and dependable.

The objective is not to build a generic model marketplace. The objective is to
make tool and capability routing predictable enough that a future gateway can
serve many hosts and providers without changing the core retrieval contract.

## 0.6 goals

1. Make indexing incremental, observable, and resource-bounded.
2. Make retrieval quality measurable with a repeatable benchmark set.
3. Make CPU/GPU behavior explicit and safe for production hosts.
4. Make background indexing reliable under concurrent API traffic.
5. Stabilize reports and metadata that a future gateway can expose as metrics,
   audit events, and billing inputs.
6. Preserve the existing `OctopusIndex` and runtime retrieval contracts.

Compatibility is a strong preference, not an absolute constraint. If a better
design requires changing a contract, the change must be intentional and
reviewed first, with a clear rationale, migration guidance, deprecation path
where practical, and regression coverage for the affected behavior.

## Explicit non-goals

- No hosted marketplace in 0.6.
- No central telemetry or prompt collection.
- No model routing implementation yet.
- No automatic execution of returned tools.
- No replacement of the host application's authentication or secret store.
- No distributed queue hidden inside the library.

## Workstream A: indexing performance

### Development

- Add a model-free synthetic benchmark command at
  `scripts/benchmark_indexing.py` that measures lifecycle timing without
  downloading models or contacting MCPs.
- Add a benchmark harness for discovery, normalization, embedding, persistence,
  and total update time.
- Harden the existing capability-signature and incremental embedding reuse
  path, then prove it with benchmarks.
- Keep incremental `add()` incremental; the current implementation already
  avoids re-embedding unchanged capabilities, and 0.6 must benchmark and
  protect that behavior. Never rebuild the entire embedding set
  unless the operation is explicitly a full `update()` or replacement.
- Add configurable embedding batch size and concurrency-safe job execution.
- Add an opt-in real-provider mode to the benchmark for cached CPU/GPU model
  throughput and memory measurements; model downloads remain disabled.
- Record counts for discovered, unchanged, added, changed, removed, failed,
  and embedded capabilities.
- Ensure failed jobs preserve the last published snapshot.
- Define an explicit local snapshot-retention policy. The current versioned
  local store preserves every published snapshot; 0.6 must either expose a
  safe retention option or document the storage-growth tradeoff before
  changing the default.

### Acceptance criteria

- The synthetic benchmark runs in a clean consumer environment and emits
  machine-readable JSON.
- Adding one new source does not embed unchanged capabilities.
- A failed update leaves retrieval against the previous snapshot working.
- Two concurrent jobs for one index never mutate the snapshot concurrently.
- Indexing latency and memory are reported for every completed job.
- Snapshot growth is measured separately from active snapshot size.

## Workstream B: retrieval benchmark

### Development

- Create a small versioned benchmark corpus containing:
  - natural-language queries;
  - expected capability IDs;
  - acceptable alternative capabilities;
  - explicitly irrelevant capabilities;
  - source allowlists where relevant.
- Run the corpus against local retrieval, pgvector retrieval, and MongoDB
  fallback/native retrieval where available.
- Measure recall@k, precision@k, irrelevant-tool rate, empty-result rate,
  latency, candidate count, and active-context size.
- Add regression thresholds so retrieval changes cannot silently degrade.

### Acceptance criteria

- Every benchmark case produces a structured result.
- Baseline metrics are checked into the repository.
- A retrieval implementation can be compared without changing the public
  `retrieve()` API.
- Benchmark data contains no credentials or private production capability
  descriptions.

## Workstream C: resource and device control

### Development

- Make device selection explicit: `auto`, `cpu`, or `cuda`.
- Report selected device, embedding model, dimensions, and batch size.
- Add safe CPU fallback when CUDA is unavailable or unusable.
- Make batch size configurable and reduce it after recoverable GPU OOM where
  safe; otherwise return a clear actionable error.
- Ensure a process does not implicitly use every visible GPU.
- Add startup diagnostics suitable for containers.

### Acceptance criteria

- CPU-only hosts initialize and retrieve successfully.
- A selected GPU is the only GPU used by the process.
- GPU OOM does not corrupt the index or lose the previous snapshot.
- Device behavior is covered by mocked tests and one real-device smoke test
  when hardware is available.

## Workstream D: background indexing contract

### Development

- Keep the 0.5.9 job API stable while improving reports and progress states.
- Add a lightweight progress callback or pollable counters without requiring
  telemetry.
- Test coalescing, rejection, waiting, cancellation, shutdown, failure, and
  recovery under concurrent retrieval traffic.
- Document that the queue is process-local and must have one owner per index.

### Acceptance criteria

- Retrieval remains available against the last successful snapshot while a
  job is running.
- `close()` never publishes a partial snapshot.
- Pending jobs have deterministic cancellation status.
- Job reports are JSON serializable and safe for a host API response.

## Workstream E: gateway-ready metadata

The library should expose optional local metadata, not send data anywhere.
Candidate fields:

- operation and job ID;
- index identity and snapshot identity;
- retriever selected;
- device and embedding model;
- candidate count and selected count;
- intent, embedding, candidate-search, and selection durations;
- active-cap and TTL decisions;
- source IDs/MCP URLs selected;
- failure category, without secrets or full prompt text by default.

The host or future gateway can turn this into metrics, audit records, routing
analytics, and eventually marketplace quality signals.

## Test protocol

### Unit tests

- source fingerprinting and unchanged-capability detection;
- embedding cache hits and misses;
- report serialization;
- device selection and fallback;
- queue state transitions;
- snapshot preservation after failure;
- retriever selection and empty-index behavior.

### Integration tests

- local index lifecycle: create, add, update, reopen, retrieve;
- PostgreSQL snapshot persistence and pgvector retrieval;
- MongoDB snapshot persistence and native/fallback retrieval;
- Redis session continuity during background indexing;
- concurrent retrieval while indexing;
- repeated process restart without accidental replacement;
- MCP headers and source discovery failure handling.

### Performance tests

Run each scenario with 10, 100, 1,000, and 10,000 synthetic capabilities:

- initial index creation;
- one-source incremental add;
- full update with no changes;
- update with 1%, 10%, and 100% changed capabilities;
- concurrent retrieval during indexing;
- CPU versus GPU embedding where hardware exists.

Capture wall time, peak RSS, GPU memory, embedding count, persisted snapshot
size, retrieval latency, and result quality metrics.

### Consumer validation

For every release candidate:

1. Build wheel and sdist locally.
2. Install the wheel into `octopus_smoke2`.
3. Install the wheel into `octopus-agent`.
4. Run a minimal public-API smoke script in both projects.
5. Run each project's relevant tests without editable-install fallback.
6. Verify package version, imports, index lifecycle, background jobs, and
   retrieval against a disposable index.
7. Run the GitHub matrix on Python 3.12 and 3.13 for Linux and Windows.

## Release gates

0.6 cannot be released unless:

- focused and full non-external tests pass;
- benchmark results are recorded;
- no regression exceeds its documented threshold;
- consumer wheel smoke tests pass in both reference projects;
- CPU behavior is validated;
- GPU behavior is validated when a GPU runner is available;
- documentation examples execute successfully;
- the wheel and sdist contain no tests, credentials, caches, or benchmark
  secrets.

Release review must explicitly identify any intentional contract changes and
confirm that they are documented in the release notes.

## Implementation order

1. Add capability fingerprints and incremental embedding reuse.
2. Add structured indexing and retrieval reports.
3. Add benchmark fixtures and regression thresholds.
4. Add explicit device and batch controls.
5. Expand background-job concurrency and failure testing.
6. Validate local, PostgreSQL, pgvector, and MongoDB consumers.
7. Update documentation and release notes.
8. Build, consumer-test, run CI, and publish 0.6.

Only after these gates pass should we design the managed capability gateway and
marketplace layer on top of the library contracts.
